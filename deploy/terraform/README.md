# Terraform for a container + database application

Two independent Terraform roots that deploy the same container image and a managed
Postgres to Google Cloud (`gcp/`) or AWS (`aws/`). They mirror each other on purpose:
same variable names, same outputs, same layer toggles, same-named modules. Learn one,
and the other reads the same way. Nothing is shared between them at runtime.

| Layer | GCP | AWS | Toggle |
| --- | --- | --- | --- |
| Base (always on, free or cents) | 7 service APIs + Artifact Registry repo | VPC (2 AZ, no NAT) + ECR repo | none |
| Database | Cloud SQL Postgres 17 `db-f1-micro` | RDS Postgres 17 `db.t4g.micro` | `create_db` |
| Serverless containers | Cloud Run v2, 0..5 instances | ECS Fargate behind an ALB, 1..5 tasks | `image != ""` |
| Kubernetes | GKE zonal, spot pool 1..4 | EKS, managed spot node group 1..4 | `create_k8s` |

Each root is composed of local modules with the same names on both sides:
`registry`, `database`, `serverless`, `kubernetes` (AWS also has `network`).

## The contract

Variables identical on both roots:

| Variable | Default | Meaning |
| --- | --- | --- |
| `name` | `experiment-go` | Prefix for every resource name |
| `region` | `europe-north1` / `eu-north-1` | Region |
| `image` | `""` | Full image reference; empty = no serverless service |
| `container_port` | `8080` | Port the container listens on |
| `health_check_path` | `/healthz` | Path the platform probes |
| `env` | `{}` | Extra env vars merged over the defaults in `locals.tf` |
| `create_db` | `false` | Managed Postgres |
| `db_name` / `db_user` | `experiment` / `app` | Database and application user |
| `db_engine_version` | `17` | Postgres major version |
| `create_k8s` | `false` | Kubernetes cluster |
| `k8s_namespace` / `k8s_service_account` | `experiment-go` | Must match `deploy/k8s` |
| `k8s_node_count` / `k8s_node_type` | `2` / `e2-standard-2` or `t3.medium` | Spot pool size and type |
| `serverless_min_instances` / `_max_instances` | `0` or `1` / `5` | Fargate cannot scale to zero |
| `serverless_cpu` / `serverless_memory` | `"1"`,`"512Mi"` or `"256"`,`"512"` | Platform-native units |

GCP only: `project_id` (required), `zone`, `registry_repo`. AWS only: `vpc_cidr`.

Outputs identical on both roots: `image_base`, `db_host` (Cloud SQL connection name or
RDS endpoint), `db_password_secret` (Secret Manager id or Secrets Manager ARN),
`serverless_url`, `k8s_cluster_name`, `k8s_credentials_command`.

## How the pieces connect

- The database password is generated by Terraform (`random_password`) and stored in
  Secret Manager / Secrets Manager as `<name>-db-password`. It never appears in a
  tfvars file. `make k8s-secret` copies it into the cluster; `make sql-psql` reads it.
- The serverless platform receives `DATABASE_URL` as a secret reference. The root
  composes the URL (`locals.tf`) into a second secret `<name>-database-url` and hands
  its id/ARN to the `serverless` module. The module only grants read access and wires
  the env var; it never sees the value.
- Kubernetes pods get `POSTGRES_*` from a ConfigMap plus the password from the
  `experiment-go-db` Secret (see `deploy/k8s`). On GKE a Cloud SQL Auth Proxy sidecar
  provides localhost; on EKS pods connect to RDS directly with TLS.
- Layer toggles are files. The `make` wrappers write `db.auto.tfvars`,
  `serverless.auto.tfvars` and `k8s.auto.tfvars` next to the root and run
  `terraform apply`; teardown removes the file and applies again. Every apply
  converges on the full declared state, so deploying one layer never destroys another.
- Ordering: serverless requires the database (a precondition fails the plan otherwise),
  so tear down serverless before the database, or use `make teardown-all` /
  `make aws-teardown-all`.

## Reusing this for another application

1. Copy `gcp/` or `aws/` (or both) into your repo.
2. Edit `locals.tf`: the `app_env` map and, if your app wants `POSTGRES_*` variables
   instead of a single `DATABASE_URL`, the `secret_env` wiring in `main.tf`
   (pass `module.database[0].password_secret_id` / `password_secret_arn` under the
   variable name your app expects).
3. Set `name`, `image`, `container_port`, `health_check_path` in `terraform.tfvars`
   or through `-var` flags.
4. Replace `deploy/k8s` with your own manifests if you use the Kubernetes layer; the
   overlays only need the `experiment-go-db` Secret name and the placeholders.
5. Keep the modules untouched. If you need a different database engine or a NAT
   gateway, change the module, not the root.

## State and backends

State is local (`terraform.tfstate` inside each root, gitignored) and contains the
database password in plain text. For anything beyond experiments, move it:

```hcl
# gcp/versions.tf
terraform {
  backend "gcs" {
    bucket = "YOUR_PROJECT-tfstate"
    prefix = "experiment-go"
  }
}

# aws/versions.tf
terraform {
  backend "s3" {
    bucket       = "your-tfstate-bucket"
    key          = "experiment-go/terraform.tfstate"
    region       = "eu-north-1"
    use_lockfile = true
  }
}
```

then `terraform init -migrate-state` in that root.

## Why two roots and not one

Terraform providers cannot be conditional. One root that "selects a cloud" would need
credentials for both on every run and would plan against both APIs. Two roots keep each
cloud's blast radius, credentials and state separate; the shared contract keeps them
easy to compare.
